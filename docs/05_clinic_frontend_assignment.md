# クリニック画面（フロントエンド）担当者向け指示書

## 1. 目的

現在のクリニック画面を、全国の美容クリニックを地域・施術条件で探せる画面へ拡張する。さらに、シミュレーション時に入力した地域、希望部位、予算、ダウンタイム、重視項目を使い、条件に合うクリニック候補をシミュレーション結果にも表示する。今回の担当範囲は画面側のみとし、データ収集・Firestore登録・定期更新などのバックエンドは別担当が実装する。

画面担当者は、用意された仮データまたはバックエンドAPIのレスポンスを使って一覧・詳細・検索機能を作る。Google Places APIや公式サイトへ画面から直接アクセスしない。

本アプリは医療機関の優劣や治療効果を保証するものではない。広告的な順位付けや、根拠のない「おすすめ」「人気No.1」表示は行わない。

## 2. 担当範囲

担当者は次の作業を行う。

1. クリニック一覧画面の改修
2. クリニック詳細画面の作成または改修
3. 地域・施術・料金などの検索／絞り込みUI
4. 仮データおよびバックエンドAPIのレスポンス表示
5. 公式情報の確認状態と最終確認日の表示
6. データがない場合、取得中、取得失敗時の表示
7. PC・スマートフォン両方での表示確認
8. シミュレーション入力条件を使ったクリニック候補の取得・表示
9. クリニック検索画面とシミュレーション結果で共通のデータ取得処理を使用

認証、マイページ、履歴、シミュレーション画像生成のロジックは、この作業では変更しない。ただし、シミュレーション結果に表示するクリニック候補の取得・描画部分に限り変更してよい。画像生成のリクエスト、プロンプト、Before/After画像、顔分析、履歴保存の処理には触れない。

### 今回担当しない作業

次の作業はプロジェクト責任者側で実装するため、画面担当者は変更しない。

- Google Places APIによる全国クリニック候補の収集
- 公式サイトの情報収集・解析
- Firestoreへの登録・更新・削除
- Cloud Scheduler、Cloud Run Jobによる定期更新
- 閉業・移転・料金変更の検知処理
- APIキー、Secret Manager、環境変数の設定
- API利用料金、クォータ、再試行回数の制御
- 管理者による公式情報の確認・公開処理

## 3. 画面で受け取る情報

### 基本情報

- Google Place ID
- クリニック名
- 住所
- 都道府県・市区町村
- 緯度・経度
- 電話番号（取得できる場合）
- 公式サイト候補URL
- 営業状態（営業中・閉業など）
- Google Maps URL
- 営業時間（取得できる場合）
- 最終取得日時

Googleの口コミ本文や写真は今回の画面に表示しない。評価点や口コミ件数も、バックエンド側から正式に提供されるまでは追加しない。

### 公式サイトで確認された情報

以下はバックエンドから受け取り、一覧または詳細画面へ表示する。

1. 対応施術
2. 施術料金・追加費用
3. 医師名、得意分野、資格
4. 症例件数
5. ダウンタイム・副作用・リスク
6. 保証・アフターケア

各項目には次の確認情報が付与される想定で実装する。

- `sourceUrl`: 根拠となる公式ページ
- `verifiedAt`: 最終確認日時
- `verificationStatus`: `verified` / `needs_review` / `unverified`
- `notes`: 条件、注意事項、料金の範囲など

値が空の場合は推測して補完せず、「公式サイトで確認できませんでした」と表示する。空欄を「なし」と解釈しない。

## 4. 画面用データ形式

担当者は次の形式のJavaScriptオブジェクトを受け取る前提で画面を作成する。開発中は同じ形式の仮データを使用してよい。

```text
{
  id
  placeId
  name
  prefecture
  city
  address
  location
  phone
  officialUrl
  googleMapsUrl
  businessStatus
  openingHours
  treatments
  pricing
  doctors
  caseInformation
  downtimeAndRisks
  warrantyAndAftercare
  sources
  verificationStatus
  verifiedAt
  placesFetchedAt
  createdAt
  updatedAt
}
```

一覧取得と詳細取得は、次の関数またはAPIへ後から差し替えられる構造にする。

```javascript
async function fetchClinics(filters) {
  // GET /api/clinics を呼ぶ想定
}

async function fetchClinicDetail(clinicId) {
  // GET /api/clinics/:clinicId を呼ぶ想定
}
```

画面コンポーネントや描画処理からFirestore SDK、Google Places APIを直接呼ばない。`data/clinics.js` と `data/clinic-details.js` は仮データ兼フォールバックとして残し、いきなり削除しない。

### データの取得経路

利用者画面は、管理画面のHTMLやJavaScriptからデータを取得しない。データは次の経路で扱う。

```text
Google Places等で候補収集
  ↓
管理画面で公式情報を確認・入力・公開
  ↓
バックエンドがFirestoreへ保存
  ↓
利用者向けAPI（GET /api/clinics）
  ↓
クリニック検索画面／シミュレーション結果画面
```

管理画面はデータを確認・編集・公開するための画面であり、利用者画面向けのデータ配信元ではない。利用者画面は必ず利用者向けAPIから `published` のデータだけを取得する。

## 5. クリニック一覧画面

一覧画面には次の機能を実装する。

- 都道府県による絞り込み
- 市区町村または駅名によるキーワード検索
- 対応施術による絞り込み
- 料金情報の有無による絞り込み
- 公式情報確認済みのみ表示する切り替え
- クリニック名、地域、主な対応施術、確認日、公式サイトへの導線
- 条件に一致する件数の表示
- 0件時の案内

検索結果を「人気順」と表現する場合、順位の根拠が必要になる。根拠を用意できない段階では、初期表示を「地域の掲載クリニック」または「条件に合うクリニック」とする。

## 6. クリニック詳細画面

詳細画面には次を表示する。

- クリニック名、住所、電話番号、営業時間
- 公式サイトを開くボタン
- Google Mapsで確認するボタン
- 対応施術
- 施術料金と追加費用
- 医師の得意分野・資格
- 症例情報
- ダウンタイム・副作用・リスク
- 保証・アフターケア
- 各情報の出典URL
- 最終確認日
- 確認状態

料金は単一の数字に丸めず、「○円から」「範囲」「モニター条件」「麻酔代・薬代などの追加費用」を分けて表示する。

ページ下部には次の注意書きを表示する。

```text
掲載情報は各クリニックの公式サイト等を確認した参考情報です。料金・施術内容・リスク・保証条件は変更される場合があります。最新情報は必ず公式サイトまたはカウンセリングで確認してください。本サービスは医療機関や施術効果を保証するものではありません。
```

## 7. 仮データでの画面開発

バックエンド完成を待たず、次の順で画面を完成させる。

1. 東京・大阪の仮データを各3〜5院用意する
2. 一覧・詳細・検索・絞り込みを完成させる
3. `verified`、`needs_review`、`unverified` の表示を確認する
4. 情報が一部欠けたデータでもレイアウトが崩れないことを確認する
5. 読み込み中、0件、通信エラーの状態を確認する
6. データ取得部分を関数に分離する
7. バックエンド完成後、関数内だけをAPI呼び出しへ差し替える

APIのURLやレスポンス形式が未確定の場合は仮実装のままPull Requestへ記載し、独自のバックエンドを追加しない。

## 8. バックエンドとの接続ルール

バックエンド側から提供される予定のエンドポイント:

```text
GET /api/clinics
GET /api/clinics/:clinicId
```

一覧APIへ渡す想定の検索条件:

```text
prefecture
city
keyword
treatment
hasPricing
verificationStatus
page
limit
```

API接続時には次を守る。

- 検索条件はURLのクエリ文字列または引数として渡す
- 連続入力のたびに即時通信せず、検索ボタンまたはデバウンスを使用する
- 二重送信を防止する
- 読み込み中は操作状態を画面に示す
- エラー時に既存表示を勝手に削除しない
- APIエラーの詳細や秘密情報を利用者へ表示しない
- ページネーションまたは追加読み込みに対応できる構造にする

## 9. シミュレーション結果との連携

シミュレーション実行後に、入力条件に合うクリニック候補を最大5院表示する。固定データだけで順位を作らず、クリニック検索画面と同じ利用者向けAPIおよび共通取得関数を使用する。

### 使用するシミュレーション条件

- `region`: 探したい地域。都道府県が判別できる場合は `prefecture` として渡す
- `eye`、`nose`、`face`、`mouth`、`forehead`: 選択された希望部位・見た目を施術検索語へ変換する
- 各部位の自由入力: 推測で施術名に変換せず、対応可能な検索語だけを使用する
- `budget`: 希望予算
- `downtime`: 希望ダウンタイム
- `clinicPriority`: 相性、費用、ダウンタイムのどれを重視するか

部位から施術検索語への変換は1か所にまとめる。例えば、目元は「二重・目元」、鼻は「鼻」、輪郭は「輪郭・小顔」、口元は「口元・唇」、おでこは「額」として扱う。自由入力だけを根拠に具体的な医療施術を断定しない。

### 取得処理

次のような共通関数を用意し、検索画面とシミュレーション結果の両方から使用する。

```javascript
async function fetchClinics(filters) {
  // GET /api/clinics を呼び出す
}

async function fetchSimulationClinics(profile) {
  // シミュレーション条件をAPI検索条件へ変換して fetchClinics を呼び出す
}
```

現在の利用者向けAPIで使用できる条件を優先し、少なくとも次を送る。

```text
prefecture
treatment
hasPricing
verificationStatus=verified
page=1
limit=5
```

予算額やダウンタイムの厳密な検索をAPIがまだ受け付けない場合は、対応済みであるかのように表示しない。画面には「料金・ダウンタイムは各公式情報で要確認」と表示し、Pull Requestへ未対応項目を明記する。独自にバックエンドAPIを変更しない。

### 表示内容

各候補には次を表示する。

- クリニック名と地域
- 条件に一致した理由（地域、希望部位、料金情報の有無など）
- 主な対応施術
- 公式情報の確認状態と最終確認日
- 詳細画面を開くボタン
- 公式サイトを開くボタン

候補が0件の場合は、条件を無視して無関係な院を表示せず、「条件に一致する公開済みクリニックがありません」と表示する。API取得中は読み込み表示、失敗時は再試行ボタンを表示する。

候補の順番を「おすすめ順」と表現する場合は、一致理由を必ず表示する。「人気順」「ランキング」とは表現しない。

## 10. セキュリティと禁止事項

- APIキーや秘密情報をGitへコミットしない
- Google Places APIやFirestoreへ画面から直接アクセスしない
- 公式サイト以外のまとめサイトを医療情報の根拠にしない
- 症例件数、資格、料金などを推測で補完しない
- 「絶対に安全」「必ず成功」などの断定表現を使用しない
- バックエンド、認証、Firestoreルール、Cloud Run設定を変更しない

## 11. デザイン要件

- 既存のホーム、履歴、マイページと配色・ボタン・余白を統一する
- クリックできる操作は文字リンクだけにせず、既存画面と同じボタン表現を使用する
- カードを過度に重ねない
- スマートフォンで横スクロールや文字切れを起こさない
- 読み込み中、0件、エラー、未確認の状態をそれぞれ区別して表示する
- 「確認済み」「要確認」「未確認」を色だけでなく文字でも示す

## 12. 作業手順

1. 最新の `main` を取得する
2. 自分専用の作業ブランチを作成する
3. 現在のクリニック画面と `data/clinics.js`、`data/clinic-details.js` を確認する
4. 画面用の仮データと取得関数を用意する
5. 東京・大阪の仮データで一覧と詳細を完成させる
6. 検索・絞り込み、各状態表示を実装する
7. データ取得関数以外から通信処理を分離する
8. PCとスマートフォンで動作確認する
9. APIキーがGitに含まれていないことを確認する
10. 変更内容、仮データの形式、接続予定箇所、テスト結果をPull Requestに記載する
11. レビュー完了後に `main` へ取り込む

他メンバーの変更を失わないため、Cloud Runの過去リビジョンへ戻して公開しない。公開は必ず最新の `main` から行う。

## 13. 完了条件

以下をすべて満たしたら担当作業完了とする。

- 仮データからクリニック一覧を読み込める
- データ取得処理が関数として分離され、APIへ差し替えられる
- 地域と施術で検索・絞り込みできる
- シミュレーション入力条件から利用者向けAPIを呼び、候補を最大5院表示できる
- シミュレーション結果に各候補の一致理由を表示できる
- 検索画面とシミュレーション結果で同じデータ取得関数を使用している
- 管理画面のファイルや管理APIから直接データを取得していない
- クリニック詳細画面に6種類の公式情報を表示できる
- 各公式情報に出典URLと確認日がある
- 未確認情報を確認済みのように表示しない
- Google Mapsと公式サイトを別ボタンで開ける
- 0件、読み込み中、エラーの表示がある
- PC・スマートフォンでレイアウトが崩れない
- APIキーや秘密情報がリポジトリに含まれていない
- Google Places、Firestore、定期更新処理を新規実装していない
- 既存のログイン、ホーム、シミュレーション、履歴、マイページを壊していない
- Pull Requestに変更ファイル、確認方法、残課題を記載している

## 14. バックエンド担当への引き渡し情報

Pull Requestには次を必ず記載する。

- 使用した仮データのJSON形式
- 一覧取得関数と詳細取得関数の場所
- 検索条件として渡している項目
- 画面が期待するレスポンス項目
- 未実装または仮表示の箇所
- PC・スマートフォンで確認した操作
- シミュレーション条件からAPI検索条件への変換表
- 予算・ダウンタイムなど、現在のAPIでは厳密に検索できない条件

バックエンド担当はこの情報に合わせてAPIを実装し、画面側の取得関数だけを差し替える。

## 15. 今回の優先順位

最優先は、実データの大量登録ではなく、一覧・詳細・検索・確認状態の画面と、シミュレーション結果への候補表示を完成させることである。バックエンド作業やGoogle API設定には手を付けず、フロントエンドの品質と接続しやすい構造に集中すること。
