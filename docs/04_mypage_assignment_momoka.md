# momoka担当: マイページ・プロフィール・アカウント管理 実装指示書

## 目的

現在のナビゲーションにある「アカウント」を「マイページ」へ変更し、ログイン中の利用者が自分のプロフィール、パスワード、保存データ、アカウントを安全に管理できる独立画面を作る。

## 担当者とブランチ

- 担当: momoka
- ブランチ: `feature/mypage`

作業開始前に `main` を最新化してからブランチを作成する。`main` へ直接pushしない。早い段階で作業ブランチをGitHubへpushし、進捗を共有する。

## 作成・変更するファイル

- `mypage.html` を新規作成する。
- `mypage.js` を新規作成する。
- `mypage.css` を新規作成する。
- `navigation.js` の「アカウント」を「マイページ」に変更し、`mypage.html` へ移動させる。
- `server.js` はアカウント削除APIの接続に必要な最小変更だけ行う。
- バックエンド処理は可能なら `account-delete.js` に分離する。
- `tests/mypage.test.js` と `tests/account-delete.test.js` を追加する。

`server.js`、`auth-server.js`、`account-store.js`、`image-store.js` は共有ファイルである。変更前に開発リーダーへ変更内容を知らせ、大規模な書き換えをしない。

## 画面構成

### 1. プロフィール

- 表示名を表示・編集できる。
- メールアドレスを読み取り専用で表示する。
- ログイン方法を「Google」「メールとパスワード」など利用者に分かる名称で表示する。
- メール確認済みか表示する。
- 初期版ではプロフィール画像とメールアドレス変更を実装しない。
- 表示名は前後の空白を除去し、1〜50文字に制限する。

表示名の更新にはFirebase Authenticationの `updateProfile()` を使う。更新後は画面と共通ナビゲーションの表示を更新する。

### 2. パスワードとセキュリティ

- メール・パスワード利用者には、現在のパスワード、新しいパスワード、確認入力を表示する。
- 現在のパスワードで `reauthenticateWithCredential()` を行ってから `updatePassword()` を実行する。
- 新しいパスワードは8文字以上とし、確認入力と一致しない場合は送信しない。
- Googleログインだけの利用者には入力欄を表示せず、「パスワードはGoogleアカウント側で管理されています」と表示する。
- パスワード、認証資格情報、IDトークンをFirestore、Storage、ログ、HTML、URLへ保存しない。
- Firebaseの詳細な認証エラーをそのまま表示せず、日本語の安全なメッセージへ変換する。

### 3. 保存データ管理

- Firestore履歴の保存件数を表示する。上限は現在10件。
- `entry.result.images.before` と `after` から保存画像数を表示する。
- 入力設定が保存されているか表示する。
- 「保存設定を削除」「履歴と画像をすべて削除」を用意する。
- 全削除前に、削除対象と元に戻せないことを確認ダイアログで表示する。
- 削除成功後は件数を再取得し、0件になったことを画面へ反映する。

利用する既存API:

|Method|Path|用途|
|---|---|---|
|GET|`/api/account/settings`|保存設定の有無を確認|
|DELETE|`/api/account/settings`|保存設定を削除|
|GET|`/api/account/history`|履歴件数・画像数を確認|
|DELETE|`/api/account/history`|履歴と対応画像を全削除|

APIは通常の `fetch()` ではなく `window.AppAuth.fetch()` で呼び出す。画像をFirestoreへ保存したり、Storageの公開URLを作ったりしない。

### 4. アカウント削除

画面下部に、通常操作と明確に分離した「危険な操作」領域を設ける。

- 削除対象として、ログイン情報、設定、履歴、Before／After画像を明記する。
- 「削除」と入力しない限り最終ボタンを有効化しない。
- Google利用者は `reauthenticateWithPopup()`、メール利用者は `reauthenticateWithCredential()` で再認証する。
- 再認証後にIDトークンを再取得し、アカウント削除APIを呼ぶ。
- 二重送信を防ぎ、処理中はボタンを無効化する。
- 成功後はクライアント上の顔画像、結果、Blob URL、保存情報を消し、`login.html` へ移動する。

## アカウント削除API契約

新規API:

```text
DELETE /api/account
Authorization: Bearer {Firebase ID token}
Content-Type: application/json

{ "confirmation": "削除" }
```

成功:

```json
{ "deleted": true }
```

バックエンドは検証済みトークンのUIDだけを使用し、リクエスト本文やURLからUIDを受け取らない。`auth_time` が現在時刻から5分を超える場合は401で再認証を要求する。

削除順序:

1. Firestoreから対象UIDの履歴を取得する。
2. Storageの `users/{uid}/simulations/` 配下を削除する。
3. Firestoreの設定と履歴を削除する。
4. 最後にFirebase Authenticationのユーザーを削除する。

Authenticationを最後にすることで、途中失敗時に利用者が再ログインして削除を再試行できるようにする。存在しない画像や既に削除済みのデータは成功扱いにし、処理を再実行可能にする。

## 表示と操作ルール

- 画面タイトルは「マイページ」とする。
- 運用ツールとして、カードを重ねすぎず、情報をプロフィール、セキュリティ、保存データ、危険な操作の順に表示する。
- 成功、処理中、入力エラー、通信失敗を `role="status"` または `aria-live` で伝える。
- エラーや表示名を `innerHTML` で挿入せず、`textContent` を使う。
- スマートフォン幅375pxで横スクロール、ボタン切れ、文字切れが起きないようにする。
- キーボードだけでも全操作ができ、フォーカス表示を消さない。
- アカウント削除ボタンは通常の保存ボタンと見間違えない配置・色にする。

## セキュリティ要件

- 未ログイン状態ではマイページを表示せず、`login.html` へ戻す。
- 別ユーザーのUIDやメールアドレスを指定できる入力欄を作らない。
- クライアントから送られた所有者情報を信用しない。
- パスワードとIDトークンをログへ出さない。
- アカウント削除は確認文字だけで実行せず、直前の再認証も必須とする。
- 顔画像が削除できなかった状態でAuthenticationだけを先に削除しない。
- APIエラーに内部パス、サービスアカウント、詳細なFirebaseエラーを含めない。

## 必須テスト

### 自動テスト

- 未ログインでマイページを利用できない。
- 表示名が1〜50文字で検証される。
- Google利用者にパスワード入力欄を表示しない。
- 新しいパスワードの不一致を送信前に拒否する。
- 保存履歴数と画像数を正しく数える。
- 保存データ全削除で既存のFirestore・Storage削除処理が呼ばれる。
- アカウント削除APIが未ログインを401で拒否する。
- 古い `auth_time` を401で拒否する。
- リクエスト本文の偽UIDを無視する。
- Storage、Firestore、Authenticationの順で削除する。
- Storage削除失敗時にAuthenticationを削除しない。
- `server.js`、`.env`、バックエンドファイルを公開しない。

### 手動テスト

- Googleログイン利用者でプロフィール更新と再認証を確認する。
- メール・パスワード利用者でパスワード変更を確認する。
- 履歴0件、1件、10件で表示を確認する。
- 画像あり・画像なしの履歴で件数を確認する。
- 保存データ全削除後、Firebase ConsoleのFirestoreとStorageで削除を確認する。
- テスト用アカウントを削除し、Authenticationから消えることを確認する。
- PC幅と375px幅で確認する。

実在メンバーの本番アカウントを手動テストで削除しない。アカウント削除試験には専用のテストアカウントを使う。
